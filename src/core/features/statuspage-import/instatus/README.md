# Instatus reader boundary

The source is Instatus management REST saved JSON, normalized into Lamp's shared move-in planner and native targets. Its namespace is `instatus`; provider-local IDs cannot alias another provider's native rows. No provider account request was used to validate this implementation. The two fixture families are synthetic-only.

The API-key reader sends bounded, fixed-origin `GET` requests to `https://api.instatus.com` with Bearer authentication and manual redirect refusal. It selects the owner-specified page ID from paginated `/v2/pages`, then reads `/v2/:page/components`, `/v1/:page/incidents`, `/v2/:page/maintenances`, each `/v1/:page/maintenances/:id` detail, `/v2/:page/subscribers`, and `/v1/:page/audience-groups`. No filter, write endpoint, public summary fetch, or alternate origin is allowed. Every list uses `page` and `per_page=100`, continuing through a short or empty page. Exceeding byte, record, file or page limits refuses the collection without truncation.

Saved filenames start `instatus-`: `pages.json`, `components.json`, `incidents.json`, `maintenances.json`, `subscribers.json`, `audience-groups.json`; subsequent pages add `-2`, etc. Detail files are `instatus-maintenance-<id>.json`. `instatus-summary.json` is optional unchanged public-summary JSON, used only to match exact supplied incident/maintenance URLs by source ID. It is not evidence of complete history. No permalink is guessed.

The official OpenAPI 2.0.0 Component schema supplies nullable embedded parent components marked `isParent:true` and `groupId`. Parents are deduplicated; conflicting identities, cycles, unresolved references and nested groups are refused. Audience groups are access controls, never visual groups. The API help uses v2 component/maintenance lists while OpenAPI attaches these schemas to v1; only documented response fields are normalized, and deployed parity remains unverified.

Incident and update event time is `started`; `createdAt` is retained separately. Maintenance detail provides affected components. A valid explicit end is supported; an end may be derived from documented integer minutes for completed maintenance or `autoEnd:true` scheduled/active maintenance. Contradictory or missing ends are refused. Every supplied maintenance update remains source history, never a notification notice.

Only confirmed, approved, email-only subscribers become pending candidates. Unconfirmed, unapproved, unsubscribed/deleted and unsupported phone/webhook/Slack/other non-email records are reported by reason. Missing/unresolved selections and contradictory all-components preferences cannot broaden consent. Original artifact hashes cover the unchanged input; retained records omit token, secret, secure-link and component automation-email capability fields. Unknown non-capability fields pass through. API-key reflection is refused before returning saved files.

The pages list cannot prove public/select-audience access. A separate owner acknowledgement states the page and supplied history are published and unrestricted; it is not provider evidence. Known private, allow-listed, audience-scoped, secure-link or unpublished records override that acknowledgement and are refused. Importing, continuing or reviewing Cutover sends no invitation or history notification; only the existing explicit owner invitation action can send.

Source references: [official API help](https://instatus.com/help/api), [official OpenAPI repository](https://github.com/instatushq/openapi), [components](https://instatus.com/help/api/components), [maintenance](https://instatus.com/help/api/maintenances), [subscribers](https://instatus.com/help/api/subscribers), [public API](https://site.instatus.com/public-api).
